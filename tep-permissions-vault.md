# TEP-XXXX: Стандарт делегирования ограниченных полномочий для ботов и AI-агентов в TON

Motivation (мотивация)

В экосистеме Telegram работают миллионы ботов и растущее число автономных AI-агентов, которым пользователи хотят делегировать действия: оплату подписок, чтение определённых чатов, вызов on-chain контрактов. Сегодня модель доступа бинарна - бот либо получает полный доступ к кошельку через TON Connect, либо не получает никакого. Промежуточного слоя ограниченных, отзываемых, с истекающим сроком действия разрешений не существует.

Это создаёт два системных риска:


Пользователь вынужден выбирать между удобством (полный доступ) и безопасностью (отказ от автоматизации).
Компрометация одного бота или агента означает компрометацию всего кошелька пользователя, а не только той функции, которую бот должен был выполнять.


По мере роста агентной экономики (автономные AI, действующие от имени пользователей) этот разрыв станет критическим узким местом. Стандарт capability-делегирования - необходимый примитив, на котором может строиться остальная инфраструктура (репутация, групповые казначейства, верифицируемый ИИ).

Specification (спецификация)

Базовая структура capability-токена:

struct Capability {
    delegator: address;        // владелец, выдавший право
    delegatee: address;        // агент/бот, получивший право
    scope: ScopeFlags;         // битовая маска разрешённых действий
    spend_limit: Coins;        // максимум TON/jetton за период
    period_seconds: uint32;    // окно сброса лимита (например, 86400 = сутки)
    expires_at: uint64;        // unix timestamp истечения
    nonce: uint64;             // защита от replay
    revoked: bool;             // флаг отзыва
}

ScopeFlags (битовая маска):


SPEND - право тратить в пределах лимита
READ_MESSAGES - право читать указанный чат (вне сети, но привязка к ончейн-идентификатору чата)
CALL_CONTRACT - право вызывать определённый адрес контракта
SIGN_TX - право подписывать транзакции от имени делегатора в рамках лимита


Жизненный цикл:


Делегатор вызывает issue_capability(), контракт создаёт запись и эмитит событие CapabilityIssued.
Делегат предъявляет capability при каждом действии; контракт проверяет expires_at, revoked, остаток spend_limit в текущем period_seconds.
Делегатор может вызвать revoke_capability(nonce) в любой момент - немедленный ончейн-отзыв, без задержки.
По истечении expires_at capability автоматически невалидна без дополнительных действий.


Контрактные инварианты, обязательные к формальной проверке:


Сумма всех трат по одному capability в пределах period_seconds никогда не превышает spend_limit.
Отозванный (revoked = true) capability не может быть использован ни при каких условиях, даже если истечение expires_at ещё не наступило.
nonce уникален в пределах пары (delegator, delegatee) и не может быть переиспользован после revoke.


Дашборд (вне протокола, рекомендация для клиентов):
Обязательное отображение всех активных capability с делегатами, лимитами и сроками действия, кнопка мгновенного отзыва.

Rationale (обоснование решений)


Почему битовая маска scope, а не строковые разрешения: компактность ончейн-хранения и атомарность проверки в одной операции, важно при газовых ограничениях TVM.
Почему период сброса лимита, а не разовый лимит: разовый лимит не подходит для подписок и регулярных платежей агентов; period-based модель ближе к реальным паттернам использования.
Почему немедленный отзыв вместо timelock: компрометация агента требует мгновенной реакции; задержка в отзыве создаёт окно атаки.
Альтернатива, которая была отклонена: off-chain подписанные разрешения (аналог OAuth scope) без ончейн-привязки - отклонена, поскольку не даёт верифицируемого мгновенного отзыва и проверяемости третьими сторонами.
