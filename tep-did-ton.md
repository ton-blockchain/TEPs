# TEP-XXXX: Метод децентрализованного идентификатора did:ton с выборочным раскрытием атрибутов


Motivation (мотивация)

Текущая модель идентичности в Telegram - это аутентификация через номер телефона и Telegram-аккаунт, что является идентификацией платформы, а не портативной личностью пользователя. У администраторов групп нет надёжного способа проверить "это живой человек, не бот" без раскрытия персональных данных, а пользователи не могут переносить репутацию или верифицированные атрибуты (KYC-статус, возраст, завершённые курсы) между приложениями без повторного прохождения проверки в каждом.

Существующие стандарты W3C DID и Verifiable Credentials решают эту проблему в вебе, но в TON-экосистеме нет нативного метода DID, привязанного к ончейн-адресу. Регуляторное давление (включая требования eIDAS 2.0 в ЕС) также движется в сторону портативных, пользователем контролируемых цифровых идентичностей.

Specification (спецификация)

Формат идентификатора:

did:ton:<network>:<address>

Пример: did:ton:mainnet:EQD... где адрес - это адрес TON-смартконтракта, выступающего DID-документом.

DID-документ (хранится в контракте или указывается через него на off-chain storage с ончейн-хэшем):

struct DidDocument {
    controller: address;           // владелец, может обновлять документ
    verification_methods: cell;    // публичные ключи для разных целей
    service_endpoints: cell;       // опционально, ссылки на сервисы
    credential_issuers: cell;      // список доверенных издателей VC
    updated_at: uint64;
}

Verifiable Credential (VC), выпускаемая в формате SD-JWT VC:

Издатель (например, KYC-провайдер) подписывает credential с полем subject = did:ton:.... Формат SD-JWT (Selective Disclosure JWT) позволяет владельцу credential раскрыть только нужные поля (например, доказать "возраст больше 18" через STARK/SNARK-доказательство, не раскрывая дату рождения целиком).

Proof-of-personhood:
Отдельный класс credential, выпускаемый ограниченным набором доверенных издателей (биометрия с zero-knowledge доказательством уникальности, либо социальный граф верификации). Хранится так же, как и любой VC, но имеет зарезервированный type в схеме для лёгкого фильтра антибот-системами групп.

Отзыв credential:
Издатель может опубликовать ончейн-запись отзыва по хэшу credential; проверяющая сторона обязана проверять список отзывов перед принятием доказательства.

Rationale (обоснование решений)


Почему SD-JWT VC, а не полный анонимный credential (например, BBS+): SD-JWT уже имеет черновик стандарта IETF и более простую интеграцию с существующими JWT-инфраструктурами выпускающих сторон (банки, KYC-провайдеры), что снижает порог внедрения на старте.
Почему DID-документ как смартконтракт, а не просто off-chain JSON с подписью: ончейн-контроллер даёт верифицируемую историю обновлений и совместимость с существующей TON-инфраструктурой кошельков (один и тот же ключ управляет и кошельком, и идентичностью).
Почему минимальное раскрытие на уровне протокола, а не опция клиента: при дефолте "раскрывай всё" разработчики приложений в большинстве случаев не меняют дефолт; протокол должен принуждать к приватности по умолчанию (privacy by design), а не полагаться на дисциплину каждого клиента.
Совместимость: метод спроектирован как расширение существующего пространства методов did: (W3C DID Core), что упрощает интероперабельность с уже существующими держателями credential вне TON-экосистемы.
